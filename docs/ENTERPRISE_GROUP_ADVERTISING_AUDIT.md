# 企業・グループ型広告サービス 監査と最小実装計画

- 対象: ワタシワークス bunshin ／ ハッシー企業・グループ型広告サービス
- 監査対象: `main` 983da67（PR #530 まで）
- 監査日: 2026-11-12
- 性質: 読み取り専用監査と、ローカル非本番DBでの検証。Production環境、顧客データ、千ノ国メディアのデータは参照・変更していない。

## 0. 結論

既存基盤（Service = `Group` + `ServiceConfiguration`、`ENTERPRISE_PROGRAM` テンプレート、公式商品情報、参加募集 Campaign、投稿承認、専用URL、Service専用LINE、活動集計）は、企業向けグループ広告の部品として十分そろっている。新しいテーブル、新しい管理基盤、新しいAIエージェントは不要。

一方で、**Service内の参加者がCampaignへ参加する経路が無く**、Service上では「商品・広告条件設定 → 参加承認 → 投稿案生成 → 管理者承認 → 本人投稿 → 集計」を通しで実行できない。加えて、**管理者承認やキャンペーン中止がコピー時点で再確認されない**安全上の欠落がある。

**一般販売判定: No-Go**（P0 の4項目を解消し、非本番で1グループの通し確認を完了した時点で、限定先行販売の Go を再判定する）。

## 1. 調査した内容と区分

区分の定義:

- **実装済み（テストあり）**: `main` に存在し、DB統合テストまたは振る舞いテストで検証されている
- **コード上のみ確認**: `main` に存在するが、自動テストがソース文字列確認のみ、または無い
- **本番反映**: `main` へのマージ済みを示す。本監査では本番の稼働を確認していない（Production操作は作業境界外）
- **実運用確認済み**: 文書上の本番確認記録があるもの。本件対象の機能では該当記録を見つけられなかった
- **未実装**

## 4. 操作フロー（P0解消後の想定）

### 企業管理者（SERVICE_OWNER / SERVICE_ADMIN、商品・募集は CONTENT_EDITOR も可）

1. **商品情報**: 商品の事実、対象者、必須表記（例: `#PR`）、禁止表現、公式素材を登録して公開する
2. **キャンペーン**: 商品の版を選び、募集名・テーマ・対象・人数・期間を入力して開始する。投稿頻度や類似度は初期値のまま（必要時だけ「詳細設定」を開く）
3. **参加者**: 招待し、参加者ごとの利用機能を確認する。必要なら「コピー前に確認する」を有効にし、確認待ちの投稿案を許可・見直し依頼する
4. **成果確認**: 参加者数、投稿案作成、採用、コピー、投稿完了（本人申告）、専用URL利用を確認する。外部実績が無い指標は表示しない
5. 中止・締切: 以後の生成・通知・コピーが止まる（P0-3）

### 参加者（PARTICIPANT）

1. 招待から参加し、同意する（LINEまたはメール）
2. ホームに出る「参加できる募集」で「参加する」を押す（P0-1、商品割当は同時に行う P0-2）
3. LINEで届く今日の投稿案を開く。商品投稿は企業確認が済むまでコピーできない
4. 本人が内容を確認してコピーし、自分でSNSへ投稿し「投稿した」を記録する
5. いつでも参加を取り消せる（以後の商品投稿は作られない）

## 5. 既存画面を活用した最小改修計画

新しい管理基盤は作らず、`/s/{slug}/manage` 配下の既存ページを使う。

- 管理画面トップの運営メニュー先頭に4業務（商品情報 `product-packs` ／ キャンペーン `campaigns` ／ 参加者 `members`・`post-approvals` ／ 成果確認 既存の7日集計と `product-packs` の活動表）を並べ、他の項目は「その他の設定」として折りたたむ
- `CampaignAdminEditor` の5つの数値入力を `<details>詳細設定</details>` へ移し、初期値（2・1・2・60・85%）は現在のAPI既定値と同じにする。API・DBは変更しない
- 集計表示の「投稿完了」を「投稿完了（本人申告）」へ変える
- 参加者側は既存 `CampaignParticipationEditor` を `apiBase` 指定で `/s/{slug}/bunshins/{id}` から再利用する

| 観点         | 検証内容                                                                      |
| ------------ | ----------------------------------------------------------------------------- |
| ブランド     | `ServiceBrand` / 設定取得が slug で解決した Service だけを返す                |

| 商品         | Bの商品版でAの Campaign を作れない。Aの分身にBの商品を割り当てられない        |

## 7. PR単位の実装計画と受入条件

既存機能の流用 → 画面修正 → 集計改善の順。いずれもテーブル追加・新規AIエージェント・ワークフローエンジン・課金基盤を含まない。

### PR-1（P0-3, P0-4, P1-1）コピー時の広告条件の再確認

- `authorizeCopy` で Campaign 投稿案に対し、Campaign `OPEN`・期間内、本人の参加 `ACCEPTED`、Group所属 `ACTIVE`・同意済み、商品版 `PUBLISHED` を再確認する。満たさない場合は新しい理由 `CAMPAIGN_UNAVAILABLE` で拒否する（既存表示へ1文追加）
- 承認依頼がある投稿案で別案を選択したとき、同じトランザクションで承認依頼を `PENDING` に戻し、`contentSnapshot` を別案本文で更新し、監査 `RESUBMITTED` を残す
- 受入条件: 第2節の「許可される」3件がすべて拒否になる。承認系の統合テスト（作成、確認待ち、他Service、見直し、再依頼、中止後、別案）が通る。lint / typecheck / test / build / integration が通る

### PR-2（P0-1, P0-2）Service参加者の Campaign 参加

- `PrismaCampaignRepository.participant()` を、個人Workspaceの分身に加え「`bunshin.groupId = campaign.groupId` の本人所有 Service 分身」でも許可する。個人向け経路は変更しない
- `decide(ACCEPTED)` の同一トランザクション内で、本人の明示操作を同意として既存 `ProductPackAssignment` を upsert する。取消時は既存の割当解除を使う
- `/s/{slug}/bunshins/{id}` に既存 `CampaignParticipationEditor` を表示し、`/api/services/{slug}/bunshins/{id}/campaigns` を追加する
- 受入条件: Service分身で参加→週計画→投稿案生成→承認→コピー→投稿記録が統合テストで通る。他Service・他人の分身では参加できない。個人向け参加の既存テストが変わらず通る

### PR-3（P1-2, P1-3）承認ルールの整合

- 確認ルール有効化後は、確認依頼の無い商品投稿案のコピー時に確認待ちを作成（または拒否）する
- 中止・締切した Campaign の確認待ちを一覧から分け、承認操作を出さない
- 受入条件: ルール変更前の投稿案が確認なしでコピーできない。中止後の確認待ちを承認できない

### PR-4（P1-4, P1-5, P1-7）企業向け管理画面の簡素化

- 第5節のとおり。キャンペーン作成の詳細設定を折りたたみ、管理画面トップを4業務中心に並べ替え、承認画面の内容を本文・ハッシュタグ・CTAの読みやすい表示にする
- 受入条件: 詳細設定を開かずに作成した Campaign の値が従来の既定値と一致する。既存の他Service（千ノ国メディア等）のページ構成・リンク先が変わらない

### PR-5（P1-6, 第6節）集計表記とA/B分離テスト

- 「投稿完了（本人申告）」表記。クリック・問い合わせ・成約は引き続き表示しない
- 第6節のA/B分離テストを追加
- 受入条件: 分離テストがCIの integration ジョブで通る

## 8. 一般販売に向けた Go / No-Go

| 条件                                                | 現状                                                 |
| --------------------------------------------------- | ---------------------------------------------------- |
| Service上で1キャンペーンを通しで実行できる          | **No**（P0-1, P0-2）                                 |
| 中止・失効・内容変更後に広告がコピーされない        | **No**（P0-3, P0-4）                                 |
| 企業承認と本人承認が別権限で維持されている          | Yes                                                  |
| 他企業の情報・会員・Campaign・URL・実績が混在しない | Yes（既存テスト＋本監査の検証。A/B専用テストはPR-5） |
| 必須表記・禁止表現の検査                            | Yes                                                  |
| 計測できない値を0件表示しない                       | Yes                                                  |
| 本番で1グループの通し確認                           | 未実施（作業境界外。PR-1/2マージ後に運営者が実施）   |

**判定: No-Go。** PR-1・PR-2 のマージと非本番での通し確認後に「限定先行販売 Go」を再判定し、PR-3〜5 と本番1グループ確認の完了後に一般販売 Go を判定する。
